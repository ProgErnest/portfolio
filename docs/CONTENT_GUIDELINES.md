# Content and Evidence Guidelines

## Accuracy

Never invent:

- Employment dates, employer names, titles, responsibilities, or achievements.
- Project features, technologies, users, metrics, outcomes, or deployment status.
- Client approval, production usage, or business impact.
- Certifications, awards, or endorsements.

If uncertain, ask at the moment the information is needed or record it in `PENDING_INFORMATION.md`.

## Project status wording

- HSVP Hub: V1.0 functional; V2.0 redesign/refactor toward a more integrated platform in progress. It is an individual academic case study developed during an internship and defended academically. The owner has authorized publication of the high-level features and technologies provided for the project. Production deployment is unverified.
- JED: implementation complete and deployed, as confirmed by the owner. Do not add a repository link or claim client acceptance.
- Auction Bids: partial functionality available; active reconstruction.
- Library Management: V1 functional; workflow and UX improvements remain.

Re-check current status before publishing.

## Privacy

HSVP Hub involves a hospital context. Do not publish patient data, identifiable
records, real credentials, named-institution details, or real-system captures.
The owner has explicitly authorized the high-level feature categories and
technologies in the project brief; do not extend them into unconfirmed or
sensitive operational detail. Production deployment is not verified.

Do not expose private repository code or links. Public repository status must be checked before adding a link.

## Skills

Distinguish practiced skills from areas being explored. Do not inflate self-assessed proficiency. Link important claims to project evidence where possible.

## Bilingual quality

English is the default. French must be technically accurate and complete. Do not translate framework names, code identifiers, or established technical terms unnecessarily.

## Evidence hierarchy

Prefer, in order:

1. Verified application screenshots with sensitive data removed.
2. Verified public repository and documentation.
3. A working demo or recorded walkthrough.
4. A clearly labelled architecture or workflow diagram based on actual implementation.
5. Textual description where visual evidence is unavailable.

Never use generated mockups as proof of a real implemented interface.
