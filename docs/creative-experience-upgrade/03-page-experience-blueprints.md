# Page Experience Blueprints

These are content-safe blueprints for the existing English and French route
families. They describe future compositions, not implementation work.

## Global shell

**Purpose:** make navigation feel like a dependable instrument, not an
animation obstacle.

- Preserve sticky floating navigation, skip link, theme control, language
  mapping, mobile disclosure, and footer links.
- Add a restrained route coordinate and optional top progress line.
- Keep shell state stable across route transitions.
- Mobile uses a full-width disclosure panel with clear focus containment and
  Escape behavior.
- Footer closes with the EP endpoint and direct route links, not a repeated
  dashboard.

## Home — origin and direction

**Stage:** verified positioning statement and primary actions.
**Field:** EP origin node with three short, labeled trajectories based only on
  existing copy: practice, projects, and direction.
**Proof:** a project trajectory strip using approved screenshots where available.
**Interaction:** selecting a trajectory focuses its linked section; pointer depth
is subtle and optional.
**Responsive:** desktop is asymmetric; mobile becomes a vertical sequence with
  the EP field above the first project proof.
**Motion:** one hero construction and one project-entry reveal, never a cascade
  through the whole page.

## About — method and formation

Replace the static two-block feeling with an evidence progression:

1. Current practice statement.
2. “Direction, not claimed title” boundary.
3. Individual-project evidence.
4. Links to work and skills.

The progression is an editorial line, not a fabricated employment timeline.
Focus interaction may connect “software engineering” to verified project
contexts. No portrait is added without an approved asset.

## Projects — observatory and proof index

Preserve the CSS filter as the non-JavaScript baseline. On wide screens, pair
each project row with a proof surface or an explicit “text evidence” surface.
Status remains the first-class label:

- HSVP Hub: active, V1 functional / V2 in progress.
- JED: implementation complete / deployed.
- Auction Bids: partially functional / reconstruction in progress.
- Library Management: V1 functional / UX and workflows to improve.

The filter may animate a stable grid, but must not claim counts or results not
actually computed. Mobile uses a readable list with optional image disclosure.

## HSVP Hub — protected system map

Use a text-first architecture map describing published categories only:
authentication/access, administrative operations, medical operations, and
background processing. Connectors explain relationships without revealing an
institution, patient process, topology, or real capture.

Include a contribution timeline based on the verified project record:
analysis, modeling, implementation, testing, and V2 refactor. The map has a
prominent evidence boundary and no production claim.

## JED — evidence and deployment boundary

Lead with the verified status: individually implemented client project,
implementation complete and deployed. Stage the approved dashboard capture with
its fictional-example caption. A feature rail can focus:

- Sales management.
- Inventory management.
- Expense management.
- Report management.

Do not invent metrics, acceptance, repository access, deployment provider, or
business outcomes. The interaction is image enlargement and feature-to-caption
focus, with all labels available in static text.

## Auction Bids — reconstruction state

Present the sign-in capture as a small evidence artifact, clearly labeled with
fictional placeholders. The dominant visual is a reconstruction frame: stable
boundaries around an explicitly partial project, with no percentage meter.
Current/next language is allowed only when it refers to documented work, not
invented backlog.

Do not publish the repository until the `.env.prod` question in
`PENDING_INFORMATION.md` is resolved.

## Library Management — functional foundation

Split the stage between the functional V1 catalog evidence and a clearly marked
improvement lane for workflow/UX work. A static workflow diagram may show only
verified V1 relationships. The public repository link remains permitted.
Future ideas use “to improve” language and never appear as shipped features.

## Skills — evidence relationship map

Retain the honest categories:

- Software engineering.
- Systems-oriented thinking.
- Backend and REST API development.
- Systems architecture and technical leadership as a development direction.

Selecting a category may highlight project/internship contexts already described
elsewhere. Do not add proficiency bars, scores, or implied mastery. The static
view shows every relationship as text.

## Experience — progression

Use a chronological spine for the two verified internships:

- DevCode Camer, June–August 2025: backend and REST API development with
  CodeIgniter 4 and Symfony.
- HooYia, June 30–September 30, 2026: Django backend learning, mini-project,
  and progressive HSVP-Hub development.

The spine may gain an active marker while scrolling, but it does not calculate
career progress or imply outcomes. HooYia remains an external link and HSVP Hub
remains a related project link.

## Contact — open endpoint

Use a sparse closing statement and direct public channels already present. A
copy-email action can be considered only as progressive enhancement with a
visible fallback. No form or backend is introduced. The EP endpoint settles
without an infinite pulse or invented availability status.

## Bilingual and responsive contract

Every blueprint must be implemented in both route families with complete,
equivalent copy. Motion sequence order remains equivalent even when French text
wraps differently. At narrow widths, preserve reading order, captions, status
labels, and focus visibility before preserving visual alignment.
